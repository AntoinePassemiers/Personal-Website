## Consensus mechanisms

Principle of consensus:
- Safety: no issues such as double-spending or transaction conflicts.
- Finality: there is a point of no-return where transactions are permanent and irreversible.
- Liveness: any new transaction will eventually be included in the blockchain at some point.

Blockchain forking enables high liveness, but breaks finality guarantees, as the non-canonical forks will have to reverse the effects of their transactions in order to catch up with the canonical branch.

### Side chains

<lex data-category="Sidechain">Sidechain</lex> = non-canonical chain. A sidechain runs its own validation rules without relying on the main chain's consensus.

Sidechains can connect to the main chain using a two-way peg (bridge): tokens are locked on the main chain, and an equal number of tokens are created on the sidechain. To get the original assets back, the sidechain tokens are burned.

### Proof of Work (PoW)

<lex data-category="Proof of Work (PoW)"><lex data-category="PoW"></lex></lex>

In Proof of Work, miners spend electricity and computing power to secure the network.

The goal of mining is not to create new coins. Coin minting is just an incentive (a reward) for PoW, which secures the network. PoW guarantees security by ensuring that the computional effort is too large to be made by a single entity, even a high-budget one.

Ethereum's PoW algorithm is called Ethash, and is resistant to ASIC (application-specific integrated circuit) mining equipments. This means that it's difficult to build a hardware that is order of magnitude faster than GPUs, which prevents centralization of mining in specialized infrastructures.

### Proof of Stake (PoS)

In Proof of Stake, validators put cryptocurrency at financial risk to secure it.
Ethereum moved from PoW to PoS in September 2022. The `difficulty` field is still present in block headers for backward compatibility, and is set to 0. Security now comes from the risk of penalities, not the computational barrier.

## Gas and fees

Roles of gas in Ethereum: reduce the volatility of the price of ether, reward the validators for their work, prevent DoS attacks, and prevent infinite loops.

Validator fee = gas cost multiplied by the gas price
Refunded ether = remaining gas multiplied by the gas price

Gas target: how much gas should be consumed on average per block.
Determined through validators voting. Gas limit = 2 x gas target. Gas target is set to a reasonable value to avoid centralization (due to the computational workload).

## Zero-knowledge proofs

<lex data-category="Zero Knowledge Proofs"><lex data-category="Zero Knowledge (ZK)"></lex></lex>

Motivation: Verify the vality of a statement without performing all the computations required to get to the original statement. This may be useful to improve the EVM state transition function: only a few nodes execute the transactions, and then provide the proofs to all other nodes -> "Centralization"

Three principles:
- Completeness: a honest prover with a valid solution can produce an acceptable proof.
- Soundness: a prover who does not have a valid solution should not be able to convince a verifier.
- Zero knowledge: the proof reveals nothing about the solution except the fact that a valid solution exists.

The witness = the secret information that proves the statement is trusted.

Interactive and simple protocol:
Requires decomposing the validity of the solution into a set of local constraints in such a way that if all local constraints are satified, the verifier knows that the prover knows the solution. In each round, the prover proves to the verifier that one local constraint is satisfied (the prover does not know which one upfront).
Each round can be summarized as follows:
- The prover injects randomness into the solution, obtaining a temporary, modified solution. Randomization should be uncorrelated fromone round to the other to prevent the verifier from reconstructing the solution.
- The prover generates a commitment and sends it to the verifier. For example, by constructing a Merkle tree from the modified solution (with random salts), and sending the Merkle root to the verifier.
- The verifier sends a random challenge (the query) to check that a one local constraint is satisfied. Because the query is random and because of the commitment, the prover can not invent a solution satisfying the constraint without being caught.
- The prover sends a response to the challenge (a proof), consisting of the small part of the modified solution needed to verify the local constraint + their salts + the Merkle verification path.
- The verifier checks the validity of the proof.
The process repeated until statistical significance.

Detailed example for the partitioning problem: [https://www.shirpeled.com/2018/09/a-hands-on-tutorial-for-zero-knowledge.html](https://www.shirpeled.com/2018/09/a-hands-on-tutorial-for-zero-knowledge.html)

Fiat-Shamir heuristic: protocol that can turn an interactive ZK proof system into a noninteractive one.
Only two rounds:
- The prover generates a `commitment`.
- The prover computes `challenge = hash(commitment || public_inputs)`.
- The prover computes a response to the `challenge` (`proof`).
- The prover generates a `new_commitment`.
- The prover computes `new_challenge = hash(new_commitment || proof || commitment || public_inputs)`
- The prover computes a response to the `new_challenge` (a `new_proof`).
- The prover repeats the logic as many times as needed for statistical significance.
- The prover sends the commitments, challenges and responses to the verifier.
- The verifier checks everything.

These approaches only work for specific problems that can be decomposed in a particular way (e.g., the well-known partitioning problem).

### Tornado Cash

- Deposit:
  - The depositor generates the random 31-bytes nullifier $n$, the random 31-bytes secrets $s$, and computes the commitment `C = hash(n, s)`, using the Perderson hash function (Baby Jubjub elliptic-curve point).
  - The depositor sends $C$ to the smart contract, as well as the funds.
  - The smart contract inserts $C$ into its Merkle tree, and updates the root $R$. It also keeps track of the history of recent Merkle roots, to prevent invalidating upcoming proofs whenevernew deposits arrive. The Merkle tree is binary, has a depth of 20 and uses a MiMC sponge for hashing. The Merkle tree structure will be needed to efficiently prove that the commitment derived from the secret note is one of the commitments previously deposited into this pool.
- Withdrawal:
  - The client computes the nullifier `N = hash(n)` and makes it public.
  - The zk proof consists in proving that the client knows a $(n, s)$ couple that generated a leaf in the Merkle tree.
  - The zk proof has the following public inputs: $(R, N, B, L, f)$, where $B$ is the recipient address, $L$ the relayer and $f$ the relayer fee.
  - The zk private witness is made of: $(n, s, E, D)$, where $E$ is the correct Merkle path, and $D$ is the corresponding binary vector indicating how to select children during tree traversal. while $E$ and $D$ can be inferred from $C$ (since the tree is public), a malicious observer would not be able to figure out which $C$ the prover used upon deposit. $E$ and $D$ must stay private, otherwise the prover can be re-identified (i.e., matched with a depositor). Indeed, the depositor is linked to $C$, which can be recovered from $E$ or $D$.
  - The client generates a Groth16 proof. The proof established:
  $$
  \begin{aligned}
  & \exists n, s, E, D: \\
  C & = \text{hash}(n ∥ s) \\
  R & = \text{MerkleRoot}(C, E, D) \\
  N & = \text{hash}(n) \\
  \end{aligned}
  $$
  - The client sends the proof to a relayer off-chain, which will take care of paying the gas upon sending the proof to the tumbler's smart contract. This is useful because the withdrawal address is typically brand new with 0 funds.

- ERC-20: the standard for fungible tokens. Extensions: burning system, voting system
- Tokens sent to contract addresses which do not have ERC-20 capabilities are lost forever. Instead, the contract should have the ERC20 instance should be set in the constructor.
- The "approve" ERC20 workflow allows, for example, to allow an other contract (e.g. a faucet) to transfer tokens, even when the addresses of the token contract and the faucet contract are different.
- In ERC20, "transactions" only changes the state of the token contract, not the state of the recipient address -> It can be tricky for wallets to keep track of token balances. Anyway, one does not want to track all balances because they are a lot of spam/junk tokens.
- ERC-1967 proxy to move the contract's logic to another address. Allows changing the code or fixing bugs over time: https://eips.ethereum.org/EIPS/eip-1967. Storage slot for the implementation contract address is hardcoded (derived from a hash) to prevent any collision with other variables in the code.
- ERC-7201: namespaced storage layouts to prevent collisions when migrating between delegate contracts.
- ERC-2612: addition to ERC-20, allows token transfers without interacting with the blockchain (therefore avoiding gas fees). Only creates the signature, by signing off-chain messages. The actual transaction is performed by someone else. Third parties pay for the gas fees in exchange for reimbursement in ERC-20 tokens.
- ERC-223: prevents inadvertently sending tokens to contracts. It uses the `extcodesize` function to distinguish between EOAs and contracts. It gives the bytecode size, which should be 0 for EOAs. This assumption is no longer true nowadays.
- ERC-777: compatible with ERC-20. They introduce "hooks", functions called during the token transfer. The sender's hook executes, then the transfer occurs, then the receiver's hook executes. Transactions are atomic, contrary to ERC-20 where they are made in 2 stages. It also introduces an operator mechanism: operators are authorized addresses which can send and burn tokens on their behalf. Introduces severe risks of reentrancy or DoS attacks.
- ERC-721: the standard for <lex data-category="NFT">non-fungible tokens (NFT)</lex>. Builds on ERC-165. Metadata (name, description, image)is decentralized by mapping the token ID to a URI (uniform resource identifier), typically an IPFS (Inter-Planetary File System) for decentralized storage. Extension: system of royalty payments.
- ERC-1155: Multitoken standard. Builds on ERC-165. Can manage both fungible (e.g., gold in a game) and non-fungible (e.g., unique swords in a game). Each token type has its own unique ID. It enables batch operations, therefore reducing gas costs. Safety mechanism to prevent locking tokens: the receiver should implement the IERC1155Receiver interface. Extensions: burnable tokens, pausable contracts.
- ERC-1820: greater flexibility for decentralized systems.
- Standards are meant to encourage interoperability between contracts. The standards are meant to be descriptive rather than prescriptive
- EIP-165 defines a method for contracts to announce the interfaces they implement. Inherits from a base class, such as OpenZeppelin's ERC-165, and overrides the `supportsInterface` method.

<lex data-category="Oracle">Oracles</lex>: everything should be deterministic on the blockchain (otherwise consensus would be impossible) -> network nodes could only include transactions that give them an advantage (e.g., in a gambling game) -> we need external info (which can be unverified sources) -> oracles solve that issue.
Oracles bridge the gap between the off-chain world and the contracts. Oracles provide random numbers, the price of gold, the results of football games, damage verification for insurance contracts, etc.
- Immediate-read oracles (oracle contract): data can be accessed with 0 gas cost by direct lookup in the oracle contract storage.
- Publish-subscribe oracles (oracle contract + off-chain daemon): when data is expected to change. Similar to RSS feeds and WebSub. Implemented using an off-chain daemon. Examples: keeping track of interest rates.
- Request-response oracles (oracle contract + off-chain daemon + off-chain data fetcher): when data is large to be stored in smart contracts, and when users only need to get a small portion of it.
Chainlink VRF (verifiable random function): the oracle uses its private key to generate a random number off-chain, and then publishes it with the corresponding proof on-chain. The public key can be used to verify that the "random" number has not been manipulated.
Computation oracles can be used to run arbitrary functions.
ZK coprocessors (Lagrange and Brevis): enable running expensive computations off-chain while ensuring on-chain verification.
Decentralized oracles with on-chain data aggregation systems. Example: Chainlink protocol, SchellingCoin protocol (rewards reporters that report values close to the median).

- Wormhole: enable transfers between Solana, Ethereum, Binance Smart Chain, Hyperliquid and Avalanche. Uses a network of off-chain guardians to improve security.
- CCIP (Chainlink's Interoperability Protocol): uses decentralized oracles. Locks/burns tokens on the source chain, and unlocks/mints tokens on the destination chain.
- CCTP (Chainlink's Transfer Protocol): bridges USDC between different chains.
- Cosmos: implements the Inter-Blockchain Communication (IBC) protocol.
- Polkadot: secures parachains via a shared set of validators in the Relay Chain

<lex data-category="Decentralized Exchange (DEX)"><lex data-category="Decentralized Exchange (DEX) Token"><lex data-category="DEX">Decentralized exchange (DEX)</lex></lex></lex>: platform that uses smart contracts to manage transactions automatically. Examples: Uniswap, Curve, PancakeSwap, dYdX, SushiSwap, Balancer.

Order book model: difficult to use on-chain due to the blockchain speed.
<lex data-category="AMM"><lex data-category="Automated Market Maker (AMM)">Automated market maker (AMM) model</lex></lex>: prices are determined by the ratio of tokens in the liquidity pools.
$$
\Delta y = \frac{y \Delta x}{x + \Delta x},
$$
where $x$ and $y$ are the pool sizes, while $\Delta x$ and $\Delta y$ are the input and output amounts, respectively.

<details>
<summary>Mathematical details</summary>

If the trader deposits $\Delta x$ of token X and receives $\Delta y$ of token Y in exchange, the product of the two quantities should remain constant:
$$
\begin{aligned}
& & xy & = (x + \Delta x) (y - \Delta y) = k \\
& \iff \quad & \Delta y & = y - \frac{xy}{x + \Delta x} \\
& & & = \frac{yx + y \Delta x - xy}{x + \Delta x} \\
& & & = \frac{y \Delta x}{x + \Delta x}, \\
\end{aligned}
$$
for some constant $k$.
</details>

Uniswap uses the AMM model. xy = constant, where x and y represent the quantities of the two tokens in the pool. -> Price = ratio of quantities.
If prices were constant instead, arbitrageurs would have an incentive to trade against the pool until one side of the reserves is exhausted (which depends on which one is overpriced/underpriced). Same problem with linear prices. -> AMM model and its hyperbolic curve are more suitable (the asymptotic behavior makes it secure: slippage discourages traders from depleting the pool).

Impermanent loss: buy -> sell -> loss due to price difference

Lending market: loan must be overcollaterallized (due to risks of default). Interest rates are determined by the market (borrowers/lenders). If the value of the collateral falls below a certain threshold, the platform's smart contracts initiate a liquidation process. Oracles are needed for securing lending markets (to prevent flash-loan attacks from people manipulating prices on a DEX).

Flash loans

Combining a lending market with a DEX enables more complex financial instruments, such as shorting.

Using the lending market instead of your own money directly can be untaxable in many jurisdictions.

## The EVM

EVM: stack-based architecture (max 1024 words). Word size = 256 bits. "Single-threaded". Memory = volatile, byte-addressable data structure. Storage = persistent key-value data structure. Calldata = immutable data structure that always contains the bytes sent as input to the next call frame
EVM is a quasi-Turing-complete state machine: "quasi" because all execution processes are limited to a finite number of computational steps by the amount of gas available.

Examples of virtual machines:
JVM -> Java, Scala
.NET -> C#
EVM -> Solidity
Solana VM, Wasm VM, Cairo VM, Move VM, etc.

EVM implementations: Go-ethereum EVM (Go), Execution-spec EVM (Python), Revm, Evmone (C++), Besu EVM (Java), Nethermind EVM (C#)

Sandboxed copy of the Ethereum world state -> execution -> if success, the real-world state is updated to match the sandboxed version.
Sandboxed copy occurs at every recursive call.
All Ethereum nodes have to compute and maintain the last state by reexecuting all the transactions it contains.
Not great -> Ethereum will be made stateless in the future. It requires changing: Enshrined proposer-builder separation (ePBS), and Verkle trees.

Merkle tree: hash tree used to efficiently prove that any chunk of the database has not been manipulated.
The hash of each parent is obtained by hashing the concatenation of the hashes of its children.
With such data structure, it is cheaper to provide a proof regarding the balance of an address, the result of a transaction, etc.
Contrary to Bitcoin, the Ethereum state changes constantly, therefore Merkle trees need some adjustements -> modified Merkle-Patricia tries.
Merkle-Patricia tries: each node has 16 children. To retrieve a value, the key is hex-encoded, and each hex value is used to index children, one level at a time.
Used to store: state, transactions, receipts (transaction results), storage (smart contract data).

Deployment bytecode = contract initialization + runtime bytecode. Obtained by running `solc --bin contract.sol`
Runtime bytecode. Obtained by running `solc --bin-runtime contract.sol`
CREATE instruction: the contract address depends only on the state of the sender.
CREATE2 instruction: the contract address now also depends on the bytecode hash.


- No difference between code and data: everything is just bytes. The distinction appears at runtime. No contract validation at deployment time (non-existing opcodes are not detected -> only at runtime). Introducing a new feature may be a problem if a contract's logic relies on the non-existence of a particular opcode.
- JUMDEST validation: 0x5b represents the JUMPDEST opcode. When using JUMP or JUMPI, the target destination should be a JUMPDEST. However, 0x5b could also be part of push data -> Runtime analysis for accurate validation -> costly -> a map is created to avoid re-making the analysis everytime (each 0x5b is marked as valid or invalid).
- "Stack too deep" error: The EVM can rapidly access only the top 16 items of the stack. The addition "a+b+c+d+e+f+g+h+i" does not compile in Solidity because it requires creating 8 intermediate results -> 9+8 > 16.
EOF (Ethereum Object Format) solves all these issues. It isolates the stack for each function call, introducing the CALLF, RETF and JUMPF opcodes, and a return stack (separate from the original operand stack).

EVM bytecode disassemblers: Ethersplay, Heimdall
